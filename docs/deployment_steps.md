# Deployment Steps

## Objective

This document explains how to deploy the production version of the Daily Weather Forecast Email Service using AWS and Terraform.

The notebook implementation demonstrates the workflow in Google Colab. The production implementation moves the workflow to AWS serverless infrastructure.

## Full Forms and Services Used

### AWS — Amazon Web Services

AWS is the cloud platform used for production deployment.

### Terraform

Terraform is an Infrastructure as Code tool. It creates cloud resources from `.tf` configuration files.

### VPC — Virtual Private Cloud

A VPC is a private network inside AWS where cloud resources are deployed.

### Subnet

A subnet is a smaller section of a VPC. This project uses a public subnet and a private subnet.

### AWS Lambda

AWS Lambda is a serverless compute service. It runs the Python weather email function without requiring a server.

### IAM — Identity and Access Management

IAM manages permissions. It controls what the Lambda function can access.

### AWS Secrets Manager

Secrets Manager stores sensitive values securely, such as API keys and email configuration.

### Amazon SES — Simple Email Service

Amazon SES is used to send emails from AWS.

### Amazon EventBridge Scheduler

EventBridge Scheduler triggers the Lambda function automatically every day.

### Amazon CloudWatch

CloudWatch stores logs generated by the Lambda function.

### NAT Gateway — Network Address Translation Gateway

A NAT Gateway allows resources inside a private subnet to access the internet without exposing them directly to inbound internet traffic.

## Prerequisites

Before deploying, the following are required:

1. An AWS account
2. AWS CLI installed and configured
3. Terraform installed
4. OpenWeather API key
5. Sender email address
6. Receiver email address
7. Amazon SES email identity verification completed

## Important SES Note

Amazon SES stands for Simple Email Service.

Before sending email using Amazon SES, the sender email address must be verified.

If the AWS account is still in the SES sandbox, both sender and receiver email addresses may need to be verified before the Lambda function can send emails successfully.

## Step 1: Configure AWS CLI

AWS CLI stands for Amazon Web Services Command Line Interface.

It allows the user to interact with AWS from the terminal.

Run:

```bash
aws configure
```

Enter:

```text
AWS Access Key ID
AWS Secret Access Key
Default region name
Default output format
```

Example region:

```text
ap-south-1
```

## Step 2: Verify SES Email Identity

SES stands for Simple Email Service.

The sender email must be verified before SES can send emails.

In AWS Console:

```text
Amazon SES → Verified identities → Create identity → Email address → Verify
```

After creating the identity, AWS sends a verification email. Click the verification link.

If the account is in SES sandbox, verify the receiver email as well.

## Step 3: Add Terraform Variable Values

Create a file inside the `terraform/` folder:

```text
terraform.tfvars
```

This file should contain project-specific values.

Example:

```hcl
aws_region = "ap-south-1"

project_name = "open-weather-email-service"

openweather_api_key = "YOUR_OPENWEATHER_API_KEY"

sender_email = "your_verified_sender@example.com"

receiver_email = "receiver@example.com"

latitude = "12.9716"

longitude = "77.5946"

location_name = "Bangalore, India"
```

Important:

Do not commit `terraform.tfvars` to GitHub because it contains secrets.

## Step 4: Go to Terraform Folder

Open terminal in the project folder and run:

```bash
cd terraform
```

## Step 5: Initialize Terraform

Run:

```bash
terraform init
```

This downloads the required Terraform provider plugins.

## Step 6: Validate Terraform Code

Run:

```bash
terraform validate
```

This checks whether the Terraform configuration is syntactically valid.

## Step 7: Preview Infrastructure Changes

Run:

```bash
terraform plan
```

This shows what resources Terraform will create before applying changes.

## Step 8: Apply Terraform

Run:

```bash
terraform apply
```

Terraform will ask for confirmation.

Type:

```text
yes
```

This creates AWS resources such as:

* VPC
* Subnets
* Internet Gateway
* NAT Gateway
* Route tables
* Lambda function
* IAM roles and policies
* Secrets Manager secret
* SES identity
* EventBridge Scheduler
* CloudWatch log group

## Step 9: Verify Lambda Function

After deployment, go to:

```text
AWS Console → Lambda → Functions
```

Open the deployed Lambda function and check:

* Runtime
* Environment
* VPC configuration
* IAM role
* CloudWatch logs

## Step 10: Test Lambda Manually

In AWS Lambda console:

```text
Test → Create test event → Run test
```

If successful, the function should:

* Fetch weather data
* Build an HTML email report
* Send email through SES
* Write logs to CloudWatch

## Step 11: Verify Scheduled Execution

Go to:

```text
AWS Console → Amazon EventBridge → Scheduler
```

Check that the schedule is enabled.

The configured schedule should trigger the Lambda function daily.

## Step 12: Check Logs

Go to:

```text
AWS Console → CloudWatch → Log groups
```

Find the Lambda log group and review logs.

CloudWatch logs help confirm:

* Function started successfully
* Weather API call completed
* Email was sent
* Errors, if any

## Step 13: Destroy Infrastructure When Not Needed

To avoid unnecessary AWS costs, run:

```bash
terraform destroy
```

Terraform will ask for confirmation.

Type:

```text
yes
```

This deletes the infrastructure created by Terraform.

## Cost Consideration

This architecture is mostly serverless, but NAT Gateway may create cost if left running.

For a real production setup, NAT Gateway is appropriate for secure private subnet internet access. For a cost-sensitive demo, Lambda can alternatively be deployed without VPC if strict private networking is not required.

## Security Considerations

* Do not hardcode secrets in source code.
* Do not commit `terraform.tfvars` to GitHub.
* Store API keys and email configuration in AWS Secrets Manager.
* Use IAM least-privilege permissions.
* Verify SES sender identity before sending email.
* Monitor Lambda execution using CloudWatch logs.

## Summary

This deployment design converts the notebook-based demonstration into a production-ready AWS serverless workflow.

The final production workflow is:

1. EventBridge Scheduler triggers Lambda daily.
2. Lambda reads secrets from Secrets Manager.
3. Lambda fetches weather data from OpenWeather API.
4. Lambda creates an HTML weather report.
5. Lambda sends the report using Amazon SES.
6. CloudWatch stores execution logs.
